# 面向 AI Agent 的设计体系库：方案 v0.2

草案 v0.2 · 2026-10-09 · 以 v0.1 为基线重构

## 1. 先回答一个更根本的问题

v0.1 把「设计体系」当作核心资产：收集、提取、检索、套用。隐含的假设是：拥有一套好的体系，就能产出好的设计。这个假设有问题。

**设计体系是设计判断的结果，不是设计判断本身。** 一套好看的体系，是某位设计师为某份内容、某群受众、某个目的做出的一连串取舍留下的痕迹：为什么用这个字号，为什么这里留这么多白，为什么全页只有一处强调色。把痕迹搬到另一份内容上，当初取舍的理由不一定还成立。

这带来三个直接后果：

1. **复刻容易形似神不似。** 从样例里能提取的是「它做了什么」，提取不到「它为什么这样做」。套到新内容上，每个数值都对，整体却不对。
2. **我们最想突出的东西，恰恰最难存进 token。** 静态的美来自比例、节奏、对比、留白和主次之间的关系；动效的好来自时间关系和编排。它们是元素之间、整页之间的关系，而不是某个属性的取值。token 存的是词汇，美在于句子怎么写。
3. **系统里缺一个判断好坏的裁判。** 选择、提取验证、评审、反馈，都依赖对设计好坏的判断。如果全部交给 agent，就是 agent 给自己打分，结果会滑向模型的平均审美，也就是常说的「AI 味」。

还有一个外部压力：风格目录正在变成免费的公共品。ui-ux-pro-max 已经提供 79 种可检索风格、192 套配色、74 组字体搭配和按行业的推理规则；基础模型本身的设计能力也在快速提升。只做「更多、更全的风格」，护城河会越来越浅。

**v0.2 的立场**【建议】：

- 体系仍然是仓库里的核心对象，但每条关键规则都要写明理由和适用边界，并挂在具体范例上。
- 真正要积累的资产是判断：标注过的高品质范例、把需求翻译成设计决策的方法、以人的选择为准的品鉴数据。
- 人的品味是系统的最终裁判。agent 负责发散、执行和自查；人负责在几个方向里挑选，并说出喜欢和不喜欢的地方。这些选择沉淀下来，逐步校准 agent 的判断。这部分数据只属于我们自己。

## 2. 定位

【建议】一句话：让 agent 为具体的受众做出「静态耐看、动起来也讲究」的网页、PPT 与图片，并能把参考作品的设计语言神似地迁移到新内容上。

非目标：不做 UI 组件库，不做 Figma 导入导出，不做通用设计工具【已确认】；不做以数量取胜的风格目录【建议，v0.2 新增】。

术语：本文的「设计体系」指一套可迁移的设计语言，接近一份艺术指导方案，不是某家公司为自家产品维护的 design system。

## 3. 受众与需求


### 3.1 使用者：谁在用这个库

| 角色 | 是谁 | 要什么 | 痛点 |
| --- | --- | --- | --- |
| 需求方 | 团队里的工程师、产品、运营等非设计师【建议，待确认】 | 说清楚要做什么，快速拿到可用、有质感的成品 | 说不出设计术语；看得出不好看，说不出哪里不好 |
| 品味负责人 | 有设计背景的同事（如果有） | 把关方向，沉淀标准 | 时间少，不可能每件都亲自做 |
| agent | Claude Code 等 | 清晰的简报、可检索的资产、可执行的规则、能自查的工具 | 默认审美平均化；看不到自己产出的实际画面 |

由此得出两个设计要求：

1. 需求方说不出术语，所以 agent 要负责把「高级一点」「再活泼些」翻译成看得见的决定（用什么字、留多少白、颜色占多大面积、节奏多快），并用对比页让人直接挑，而不是要求人去描述。
2. 品味负责人的时间少，所以他的每一次挑选和评语都要被记录、复用，作用于以后的产出，而不只作用于当前这一件。

【待定】团队里是否有设计师能长期担任品味负责人。如果没有，就需要公认的优秀作品承担更多裁判职责，第一期的验收方式也要相应调整。

### 3.2 观看者：成品给谁看

设计的好坏是相对于观看者和目的而言的。不同载体的观看者，成功标准完全不同：

| 载体 | 典型观看者与场景 | 成功标准 | 对设计的直接影响 |
| --- | --- | --- | --- |
| 落地页 | 访客，几秒内决定留下还是离开 | 首屏讲清「这是什么、和我有什么关系」，并引导行动 | 首屏层级、视觉主角、行动按钮、滚动叙事 |
| PPT | 会议听众，跟着讲者走；会后可能被转发单独阅读 | 每页一个观点，远处看得清，讲者好讲 | 一页一个主张、字号下限、讲稿备注、翻页节奏 |
| 海报、社交卡片 | 信息流里的路人，停留一两秒 | 先被看见，再被读懂 | 远看时的明暗块面、标题冲击力、品牌识别 |

【建议】把这张表落实为体系里的意图层（见 4.1）。每次产出都先写一份设计简报：给谁看、在什么场合、希望他们记住什么或做什么、调性是什么。简报是人和 agent 对齐的地方，也是评审的依据。

【待定，最重要】团队真实的高频场景是什么，例如产品发布、融资或汇报、活动推广、内部分享。第一期的种子体系和示范产品应该从真实场景反推，而不是从风格谱系正推。

## 4. 核心概念模型（修订）

### 4.1 设计体系的五个部分

| 部分 | 回答什么 | 包含什么 | 状态 |
| --- | --- | --- | --- |
| 意图 | 为谁、为什么这样设计 | 适用的受众与场景、传达目标、调性刻度、关键规则的理由与适用边界 | 新增 |
| 视觉语言 | 长什么样 | token 层、规则层、画风层 | 三层【已确认】 |
| 动效语言 | 怎么动 | 动效 token、编排规则、动效画风、高光时刻 | 新增，见第 6 节 |
| 结构骨架 | 信息怎么组织 | 页型或区块类型、网格、信息层级、叙事顺序 | 沿用 |
| 范例 | 证据 | 体系在标准样张和真实内容上的渲染效果，以及来源作品（如有） | 新增 |

**设计产品 = 结构骨架 + 视觉语言 + 动效语言 + 示例内容**，落在某个具体载体上，是成套的成品，不是组件。

### 4.2 为什么需要意图层

意图层是迁移时的判据。换肤或换骨架时，agent 逐条检查规则的理由和适用边界。举两个例子：

- 「正文每行不超过一定字数」的理由是保证手机上的阅读体验。迁移到 PPT 时这个理由不成立，应该换成 PPT 自己的规则。
- 「全页只有一处使用强调色」的理由是让行动按钮成为唯一的主角。这个理由在任何载体上都成立，应当保留。

有了理由和边界，迁移就从「照搬数值」变成「判断哪些取舍仍然成立」。

### 4.3 视觉语言的维度（沿用 v0.1，略作调整）

v0.1 的八个维度中，「动效」移入动效语言，「气质与语气」移入意图层。视觉语言保留六个维度：

| 维度 | 专业上看什么 | 自动提取难度 |
| --- | --- | --- |
| 色彩 | 角色划分（主、辅、强调、中性、语义）、面积比例、明度结构、冷暖、对比度 | 低，可测量 |
| 字体 | 字体搭配、字阶比例、字重、行高与字距 | 低（网页）到中（图片） |
| 版面与网格 | 栏数、边距、对齐方式、留白、信息密度 | 中 |
| 形态语言 | 圆角还是直角、线条粗细、几何还是有机 | 中 |
| 层次与质感 | 靠阴影、描边还是色块区分层次；玻璃、纸张、噪点等材质 | 中 |
| 图像与插画 | 摄影处理、插画笔触、图标风格、装饰元素 | 高，需要视觉判断 |

提取结果的三种可信度沿用 v0.1：测得（脚本测量）、判读（视觉模型按评分标准判断）、推断（对设计意图的推测）。意图层几乎全部属于推断，必须由人确认。

### 4.4 迁移的方向与跨载体原则（沿用）

迁移有两个方向：换肤（保留骨架，换视觉与动效语言），换骨架（保留语言，用到新的载体或页型）。

跨载体的两条原则：

1. 存比例关系，不存绝对数值。字号存字阶比例，再配各载体的基准值；间距、圆角、动效时长存相对基准的倍数。
2. 区分两种版面范式：流式响应式（网页）和固定画布（PPT 页、海报、社交卡片）。结构骨架的 schema 因此分成两类。

### 4.5 检索与分类（调整）

检索顺序从「先风格」改为「先意图」：先按场景、受众和传达目标筛选，再按风格谱系和调性刻度排序。

调性刻度【待定】：v0.1 提出正式到活泼、极简到丰富、冷到暖。oil-ui 用五个刻度（能量、完成度、密度、分量、严肃度），taste-skill 用三个可调刻度（版面变化、动效强度、信息密度）。建议在阶段 0 选定一套，原则是每个刻度都能直接对应到看得见的设计决定。

## 5. 静态美：把能检查的部分做成检查器

（AI 起草，需设计背景复核）

目标是让「好看」中可以测量的部分自动把关，把人和视觉模型的精力留给真正需要判断的部分。

### 5.1 可检测项（脚本读取 DOM 或 SVG）

| 方面 | 检查什么 | 说明 |
| --- | --- | --- |
| 网格与对齐 | 元素边缘是否落在网格线或共同对齐线上 | 统计未对齐的边缘数量 |
| 间距节奏 | 间距是否取自体系的间距阶梯 | 出现阶梯之外的数值即报告 |
| 字阶 | 字号是否取自字阶；同一视图的字号层级数量 | 层级过多通常意味着主次混乱 |
| 行长与行高 | 每行字数、行高与字号之比 | 中文和西文分别设阈值 |
| 色彩 | 颜色数量、各角色的面积占比、对比度 | 对比度按 WCAG 计算 |
| 排版细节 | 孤字、寡行、中文避头尾、中西文混排间距 | 可参考 W3C《中文排版需求》 |
| 视觉主角 | 模糊后的明暗块面是否只有一个焦点 | 把「眯眼看」自动化：截图做高斯模糊，计算亮度与显著性分布 |

### 5.2 需判读项（视觉模型按评分标准判断，人工抽检）

主角是否唯一且明确；留白是有意为之还是空洞；整体是否有张力，还是处处平均用力；细节完成度；是否落入「AI 味」反模式。

### 5.3 反模式库

收集 agent 产出中反复出现的平庸模式，作为产出前的自查清单和评审的扣分项。起点可以参考 ui-ux-pro-max 的反模式条目（例如紫粉渐变、用 emoji 充当图标）和 taste-skill 的反 AI 味规则，再加上我们观察到的常见问题（例如所有内容居中、千篇一律的等大卡片网格），之后用自己的评审记录持续补充。

### 5.4 做减法

借鉴 oil-ui：产出的最后一步是删减。一页只留一个主角，删掉不影响理解的文字、重复的线和多余的容器。这一步写进产出流程，不靠运气。

## 6. 动效：从「加点动画」到动效语言

（AI 起草，需设计背景复核）

现有项目多把动效当作一个强度开关，例如 taste-skill 的动效强度刻度、ui-ux-pro-max 输出中的 Key Effects 一栏。我们把动效当作和视觉语言并列的一套语言。

### 6.1 动效语言的四层

| 层 | 内容 | 举例 |
| --- | --- | --- |
| token | 时长阶梯、缓动曲线集、弹簧参数、错峰间隔、位移距离 | 时长分快、中、慢几档；退场通常比入场稍快 |
| 编排规则 | 什么该动、为什么动、先后顺序、可打断、降级方案 | 主元素先动，次要元素依次跟随；尊重系统的「减少动态效果」设置；优先只动 transform 和 opacity |
| 动效画风 | 运动的性格 | 物理弹性、机械精确、电影感慢推、编辑感克制淡入；与视觉风格谱系配对 |
| 高光时刻 | 每个产品一到两处值得记住的动效，其余保持安静 | 首屏的一次揭示、提交成功时的反馈、PPT 关键数据页的出场 |

动效按目的分四类：反馈（我点到了）、导向（东西从哪里来、到哪里去）、层级（先看哪里）、叙事与情绪（记住这一刻）。每条动效规则都要标注属于哪一类，说不出目的的动效不进体系。

动效预算：动效是有限的资源，只花在帮助理解和记忆的地方。这与 oil-ui「只把一两处做到极致，其余保持安静」的思路一致。

### 6.2 跨载体

| 载体 | 动效形式 | 备注 |
| --- | --- | --- |
| 网页 | 交互反馈、入场编排、滚动叙事 | CSS 与 Web Animations API，复杂场景用 GSAP；很强的首屏动画可参考 oil-motion 用生成视频或序列帧驱动滚动动画的做法 |
| PPT | 页面切换、元素动画、平滑切换（Morph）类效果 | ppt-master 已能输出原生的切换与动画，可评估复用 |
| 静态图片 | 没有动效；可以用构图暗示运动（斜线、方向感、动态模糊） | 社交场景可选导出短视频或动图，放到后续阶段 |

同一套动效语言在不同载体上：时长和缓动的比例关系保持一致，具体形式按载体的能力映射。

### 6.3 动效的提取与评审

- 提取（网址）：用无头浏览器加载并录制。CSS 动画与过渡可通过 `document.getAnimations()` 读取时长、缓动和延迟；JS 驱动的动画逐帧采样元素位置，拟合时长与曲线；滚动驱动的动画按滚动位置采样。
- 评审：单帧截图看不出动效好坏。把动效渲染成胶片条（按时间排列的关键帧拼图）并附时间曲线图，交给视觉模型判读；时长和曲线是否在阶梯内、是否掉帧，由脚本检查；编排是否有主次，由人抽检。
- 风险：视觉模型判读动效的能力尚不确定。第一期以脚本检查加人工抽检为主。

## 7. 协作方式：一切通过和 agent 对话

【已确认】协作不在页面里填反馈，而是和 agent 交流。

### 7.1 一次产出的对话流程【建议】

1. 需求：人用自然语言说要做什么，附上素材或参考。
2. 简报：agent 写出设计简报（受众、场合、传达目标、调性刻度、载体），最多追问三个关键问题。人确认简报。
3. 发散：agent 选出两到三个明显不同的方向，各做一个小样，生成对比页。方向之间必须拉开差距，借鉴 oil-ui 的规则：骨架、字体、色彩、主视觉四项中，任意两个方向最多只有一项相同。
4. 挑选：人在对比页里看，回到对话里说选哪个、喜欢哪里、不喜欢哪里。对比页可以提供「复制一句话」按钮，把所选方向的编号和要点复制进对话（oil-ui 的做法）。
5. 深化：agent 按选中的方向做出完整成品，运行检查器和评审，自己先修一轮。
6. 交付与反馈：人看成品，在对话里提意见。agent 把意见翻译成结构化修订，并确认作用范围：只改这一件、改这套体系，还是记为团队的通用偏好。

人的介入点只有两个：确认简报与方向，验收成品。这与「需求 → 规格 → 实现 → 验证」的闭环同构，设计简报就是设计的规格。

### 7.2 偏好账本

每次挑选与评语记为一条记录：当时的简报、候选方向、选了哪个、没选哪个、理由（翻译成维度和方向）。这份账本有三个用途：

1. 校准评审：把视觉模型的判断和人的选择对比，计算一致率，据此调整评分标准。
2. 积累团队品味：反复出现的偏好提炼成团队级规则，经人确认后生效。
3. 改进检索：记录哪些体系在哪类简报下常被选中。

### 7.3 展厅的新定位

v0.1 的可交互展厅调整为两样东西：agent 按需生成的对比页（主要），以及一个只读的目录站，用来浏览现有体系与产品（次要，可后置）。不再做页面内的反馈表单。

## 8. 系统构成（修订）

### 8.1 分工原则（沿用）

知识与数据放仓库，流程放 skills。skills 是动词，仓库是名词。skills 只依赖索引和带版本号的 schema，不依赖仓库目录细节。确定性的工作写成脚本，只有需要审美判断的部分交给 agent，并附评分标准。

【待定】skills 套件与仓库的具体形式仍未确定。

### 8.2 能力模块

| 模块 | 职责 | 相对 v0.1 |
| --- | --- | --- |
| 简报 | 把自然语言需求整理成设计简报，必要时追问 | 新增 |
| 选择 | 按简报检索体系、产品与范例，选出发散方向 | 调整：先按意图，再按风格 |
| 产出 | 按载体产出小样与成品 | 沿用 |
| 对比 | 生成对比页，收集挑选结果 | 新增 |
| 提取 | 从参考样例提取体系草稿，包括意图推断与动效 | 扩充 |
| 迁移 | 换肤或换骨架，按意图层判断规则是否仍然成立 | 扩充 |
| 品鉴 | 检查器加视觉评审，输出逐维度结论与修改建议 | 原「评审」，扩充了静态美与动效 |
| 学习 | 把对话中的反馈写入偏好账本，提炼规则提案 | 从原「入库与维护」中独立出来 |

### 8.3 仓库内容

- 体系：意图、视觉语言、动效语言、结构骨架。
- 设计产品：成套产品，引用体系，附示例内容。
- 范例库：高品质参考作品，以及本库产出中被选中的作品。每条范例标注它在哪些维度上出色、为什么出色、适合什么场景。这是「判断」最直接的载体。
- 原则与反模式：维度定义、风格谱系、调性刻度、静态美与动效的评分标准、反模式清单。
- 标准样张：一份固定的示例内容，在每套体系下渲染，使对比公平。
- 工具：提取器、渲染器（网页截图与录屏、PPT、图片）、静态检查器、动效检查器、对比页生成器。
- 偏好账本：结构化的挑选与反馈记录。
- schema 与索引：由脚本生成，记录 ID、标签、意图、载体、风格谱系、调性刻度和路径。

### 8.4 与现有项目组合【建议】

不必样样自建：

- PPT 输出：评估把 ppt-master 作为 PPTX 渲染后端，我们负责把体系翻译成它能消费的输入。它在原生可编辑 PPTX 上积累很深，自研成本高。
- 格式兼容：体系可以导出为 DESIGN.md，方便在其他工具中使用。
- 检索：ui-ux-pro-max 的 BM25 加 CSV 方案简单可用，第一期可以照搬思路。

## 9. 关键流程（修订）

### 9.1 产出

见 7.1。

### 9.2 提取

1. 输入参考样例。网址：读取计算样式、截图、录制动效。图片：视觉模型加取色聚类。
2. 生成体系草稿，五个部分逐项填写，每个字段标注来源类型（测得、判读、推断）与置信度。意图层交给人确认。
3. 复现测试：用草稿体系重做原样例的内容，逐维度与原样例对比，验证「抄得像」。
4. 迁移测试：用草稿体系做一份完全不同的内容（标准样张），请人判断是否仍然一眼看出是同一套语言，并且依然好看，验证「学得会」。
5. 两项都通过才入库；不通过则回到第 2 步修订。

迁移测试是 v0.2 新增的关键一步。只做复现测试，提取器可能只是学会了照抄这一页。

### 9.3 迁移

确定迁移方向，保留不变的部分，替换另一部分；对每条规则按意图层判断是否仍然成立，不成立的换成目标载体的对应规则；然后走品鉴。

### 9.4 品鉴

不做像素级对比，而是逐维度评分：测得项用脚本，判读项用视觉模型按评分标准判断，并持续与偏好账本中人的选择比对。一致率达到目标后，才逐步减少人工抽检。

## 10. 现有项目与差异化（修订）

### 10.1 格局

| 类型 | 代表 | 强项 | 对我们的意义 |
| --- | --- | --- | --- |
| 规范格式与合集 | DESIGN.md、awesome-design-md | token 格式与品牌合集 | 作为导出格式兼容 |
| 风格数据库加推理 | ui-ux-pro-max | 风格、配色、字体、落地页模式的大规模目录与行业规则 | 不在数量上竞争；借鉴检索与反模式 |
| 设计方法 skill | oil-ui、taste-skill | 定调性、拉开方向、对比页、反 AI 味、做减法 | 借鉴流程；它们重方法，资产沉淀较少 |
| 载体引擎 | ppt-master | 原生可编辑 PPTX、先理顺论证再设计、从参考提炼模板 | 评估作为 PPT 后端 |
| 网址与图片提取器 | iFurySt/DESIGN.md、arvindrk/extract-design-system、anydesign 等 | 从网页或图片提取 token | 多数产出文件后即结束，缺验证 |
| 整合平台 | Open Design | 内置体系多、载体全 | 参照其产品形态 |

v0.1 对 DESIGN.md 格式的说明仍然有效：截至 2026 年 6 月仍处于 alpha（v0.2.0），以它为基础扩展需预留版本兼容。

### 10.2 新参考项目的借鉴点

- ui-ux-pro-max：从产品类型推出风格、配色、字体和落地页模式的推理规则；按行业区分的反模式；交付前检查清单；「主文件加页面覆盖」的体系持久化方式。
- oil-ui：先认品类，看同类中最好的作品；用五个调性刻度把「高级」「简洁」这类形容词翻译成看得见的决定；从具体的材质、场景或角色出发，而不是从形容词出发；先问首屏给谁看；方向之间强制拉开差距；只做一两处让人记住的地方；对比页加「复制一句话给 agent」的挑选方式；以实际截图为准的独立评审。
- taste-skill：三个可调刻度；先生成参考图、再分析、再写代码的图像优先流程，可以用于画风层；改造已有项目时先审计再动手。
- ppt-master：原生 PPTX 输出与原生动画；先把论证理顺再做设计；从参考中提炼品牌、风格、版式模板；多种画布规格（含小红书、微信等社交尺寸）。它明确表示「工具只负责流程，模型决定上限」，这对我们设定期望值也有参考意义。

### 10.3 差异化收敛为三点【建议】

v0.1 列出的五个空白中，「偏 Web」已被 ppt-master 等项目部分覆盖，「面向检索的组织」已被 ui-ux-pro-max 覆盖。v0.2 收敛为：

1. **美可以被检查**：静态美中可测量的部分做成检查器，不可测量的部分由标注范例和经过人校准的评审把关。
2. **动效成体系**：动效是和视觉并列的语言，有 token、编排规则、动效画风和高光时刻，能从网址中提取，并跨载体映射。
3. **迁移后仍然神似**：意图层加迁移测试，让提取和复用不止于抄数值。

贯穿三点的底座是偏好账本：系统越用越贴近团队自己的品味。

### 10.4 版权（沿用）

从品牌网站提取的数值来自公开 CSS，并非官方设计规范。每套体系记录来源与授权状态，区分「复刻某品牌」和「受其启发」。对外发布的体系建议只收录「受其启发」的。

## 11. 第一期范围与路线（修订）

第一期载体【已确认】：网页落地页、PPT、静态图片（海报或社交卡片）。

| 阶段 | 内容 | 验收标准（草案） |
| --- | --- | --- |
| 0 对齐 | 确定一到两个真实高频场景；写简报模板；选定调性刻度；手工撰写 3 套种子体系（含意图与动效）；收集并标注约 30 个范例；检查器 v0 | 团队评审通过；种子体系覆盖真实场景 |
| 1 用起来 | 跑通「简报 → 发散 → 对比页 → 挑选 → 成品」的完整对话流程；三个载体各一个成套产品，落地页含一处高光动效，PPT 含切换与关键页动画；偏好账本开始记录 | 盲测：同一批简报下，「agent + 本库」对「agent 裸跑」和「agent + 现有 skill」的胜率明显过半（目标值待定）；换肤后骨架保持不变 |
| 2 提取与品鉴 | 网址提取（含动效）、图片提取；复现测试与迁移测试；视觉评审校准 | 提取出的体系通过迁移测试；评审与人的选择一致率达到目标值（待定） |
| 3 扩充 | 完善迁移；提炼团队偏好；扩充体系与范例；优化检索；静态图的动态导出 | 待定 |

顺序理由：先验证「用」，再做「提取」，理由同 v0.1。补充一点：阶段 1 的盲测是整个项目的第一道关口。如果用了本库的产出在盲测中赢不了裸跑的 agent，后面的提取和扩充都失去意义，应当先回头修正方向。

## 12. 待定问题

按重要性排序：

1. 团队真实的高频场景与观看者是谁。这决定种子体系、示范产品和盲测题目。
2. 品味负责人：团队里是否有设计师能长期参与挑选与校准；如果没有，裁判来源如何替代。
3. PPT 后端：复用 ppt-master，还是自建。
4. 静态图片的生成方式：HTML 渲染成图、调用图像生成模型，还是两者结合（模型生成画风素材，HTML 负责排版）。这决定画风层能做到什么程度。
5. 动效评审的可靠性：视觉模型能否判读胶片条，第一期需要多少人工。
6. 意图层的表示：理由与适用边界写成文字规则，还是半结构化字段。
7. 结构骨架的 schema 如何表达。v0.1 已指出这是最大的设计风险点，仍然成立。
8. 调性刻度用哪一套。
9. 形态：skills 与仓库是否放在同一个仓库；skills 如何定位仓库根目录；目标 agent 范围。
10. 存储格式：以 DESIGN.md 加 DTCG 为基础扩展，还是自研 schema 再导出 DESIGN.md。
11. 盲测的设计：题目、评委、目标胜率。
12. 提取样例的版权与授权策略。
