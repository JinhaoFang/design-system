Spec #65 工具改进：命令手册重排、截图验收工具

spec #1 复盘里的两处工具问题都解决了：命令手册改成每个命令一节、一条事实一行，加了长行检查；网页构建会顺带产出分段截图和首屏入场抽帧拼图，验收时不用再手写切图命令。两张工单都已关闭。PR 等你审核合并。

任务

  • 目标：解决 spec #1 执行中暴露的两处工具问题。一是命令手册难读、容易冲突：一行最长 1,971 字，spec #1 期间 18 次提交改它，两次合并停在它的冲突上。二是截图验收靠手写命令：执行会话里 21 次手写 ffmpeg 切图、拼抽帧，两次因为没装 PIL 重来。
  • 范围：#66 命令手册；#67 网页作品的验收截图；收尾审查后的返工 #70；PR 上 CI 失败后的返工 #72。幻灯片、社交配图的拼图不做。
  • 结果：pnpm verify 通过（ 项）；CI 恢复通过，design-system 的 CI 从 10-13 起一直是红的。收尾审查见「质量」一节。

命令手册（#66）

  • 设计负责人角色文档的验收一节写明：网页作品看分段截图和拼图，不手写切图命令。

决定

决定谁理由
截图和拼图只用 Playwright 和 Node，不用 ffmpeg设计负责人（你授权）构建本来就用 Playwright 录屏，不多一个系统依赖，CI 和别的机器直接能跑
#66 返工时放开「逐字不变」，改成按事实核对设计负责人逐字不变只能在逗号处硬折行，179 行是半句话，读起来没有变好

长行上限 160 字；分段高度 900 / 844px；抽帧间隔 200msCodex 推断，设计负责人接受能放下一条完整的事实；和现有视口一致；一张拼图在 Read 里看得清

问题处理

设计负责人的失误：「不用 ffmpeg」是我替你定的，写进了 spec，却没在回复里单列。你读 spec 时发现和复盘时的说法对不上。当时补了说明，你授权我定。规则改成：替你定的事在回复里单列，和之前说的不一样时点明。
重装 run-spec 后 skills-lock.json 没提交，主工作区不干净，land 会拒绝合并 #66。锁文件放进 PR #69 提交；video-studio 的安装说明写明重装后要提交。
CI 红了两天没人发现：一条回归用例从 10-13 起在 CI 上每次都超过 60 秒，main 也是红的，PR #55、#68 都是带着失败合并的；路线图把它记成「偶发」。原因是 spec #1 加的字体子集和打印媒体采集让构建变慢，这条用例 10-12 时在 CI 上已经要 48 秒。#72 把用例的构建从 19 次减到 7 次，CI 上 31.7 秒，断言比原来多。video-studio 的 run-spec 收尾改成等 PR 上的 CI 跑完再交。
#67 的入场抽帧在 CI 上截图失败，拖垮了构建；本机三次全量验证都没出现。#72：失败帧重试一次，仍失败就跳过、记录阶段和原因，拼图上标出；拼图合成挪到录屏保存之后，不再挡住录屏。
#67 第一版的分段文件名排在整页截图前面，抢了样张缩略图。Codex 自己跑全量验证时发现，改名为 web-segment-<宽度>-<编号>.png。
#66 第一轮交回后，验收隔了一天半才做（10-13 23:54 交回，10-15 11:20 才验收）。中间在等第一轮改进的复核，属于排期，不影响结果。

流程发现

  • 规则放错了阶段：「先做定稿」「方向先给用户看」原来只写在执行技能里，可这两类决定发生在写 spec、拆工单的时候。已移进设计负责人角色文档的「工作流」（PR #69）。
  • 「难回头」要有标准：换不换 ffmpeg 只影响一个工具，不算难回头；缺的是替你定的事没有单列。照「技术选型都要问」去改，会把每个细节都推给你。
  • PR 上的 CI 不能不看：集成分支推送不跑 CI，land 只在本机验证，PR 上的 CI 是整个 spec 唯一一次在 CI 环境里跑。这次它抓到了本机复现不了的截图失败。
  • 这几条连同证据记在 video-studio 的 docs/research/run-spec-migration.md「第一轮改进之后」（问题 33～40）。
