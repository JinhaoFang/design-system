# 应用界面纳入范围：给成熟组件库套体系，不自建组件库

应用界面从非目标改为第 2 阶段的载体（2026-11-11 用户提出，阶段位置和定位交设计负责人定）。agent 做应用界面时几乎都直接用组件库的默认主题，产出彼此雷同，这正是本库要解决的「审美趋于平均」，而且需求方日常的需求里应用界面比展示型网页更多。本库不自己写组件：按钮、弹层、表单这些组件的行为、无障碍和状态逻辑交给成熟组件库，本库只提供两样东西，一是体系落到组件库上的主题包，二是体系里写给应用界面的规则。具体用哪些库在进入第 2 阶段时再调研和确认，范围不只是组件，还包括动画、交互、图标、图表等各方面；11-11 初步看过的候选有 shadcn/ui、Base UI、HeroUI、Detent，它们都已改用 CSS 变量和 Tailwind v4 定制外观，可行性没有问题。

放在第 1 阶段之后：应用界面要复用第 1 阶段写好的产出流程、技能和词典，如果盲选输了、方向要改，提前做的应用界面会跟着返工。放在提取之前：先定下体系在应用界面上要写哪些东西，提取时才知道一份完整的体系草稿该包含什么。

## 考虑过的方案

- **自建组件库**：工作量大，而且会和方案定的「不做 UI 组件库」相冲突，没有收益。
- **只出 CSS 变量主题**：只能换颜色、圆角和字体，体系的材质、动效手感和状态规则都带不过去，做出来就是同一个界面换了几种颜色。
- **同时平等支持多个组件库**：每个库的语义变量和组件结构都不一样，平摊精力会让每份适配都做不深。调研时应定一个参考实现，其余只用来验证体系没有绑死在某一个库上。

## 后果

- 方案第 2.1 节的非目标改为「自建 UI 组件库」，应用界面不再是非目标；第 8 节加入第 2 阶段，原来的提取、扩充顺延为第 3、第 4 阶段。
- 体系可以写明「不适合应用界面」，这本身就符合美学立场的「地气」一条。
- 选定的库版本要固定，主题包跟着库升级，这是新增的维护成本。
