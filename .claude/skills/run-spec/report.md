# spec 汇报的写法

汇报是设计负责人向用户汇报工作：这次做了什么、做成了什么、花了多少、遇到什么、接下来做什么。它不是交给用户检查的中间产物。下面是默认内容，按每次的情况取舍。

## 形式

- 汇报是一个 HTML 可视化页面，单个文件，存进汇报目录，文件名 `spec-<S>-<英文短名>.html`。样式、脚本和数据都写在文件里；外部资源只用 Google Fonts，并写好系统字体的后备。
- 版式沿用上一份 HTML 汇报：复制它，换掉内容和数据，各期保持一致、方便对照。
- 这几项用图表或图示，不用大段文字：关键数字一行；派发时间线（每次派发一条横条，看得出并行和返工）；两边用量和上一期的对比；审查发现表。执行流程或工作方式有变化时，加一张改后的流程图。其他部分用短句和表格。
- 深浅色都要可读，手机宽度下不横向滚动；图表要有文字标注或数据表，不能只靠颜色区分。
- 写成完整的 HTML 文档（`<!doctype html>`，`<head>` 里放 charset、title 和样式），本地浏览器直接打开。
- 交给用户：给出文件路径。不发布到 claude.ai 或其他外部服务。

## 要有

- **任务**：目标、范围、一句话结果（含 PR 和 CI 的状态）。
- **交付**：交付了什么，对用户意味着什么。
- **时间线**：关键节点。
- **成本与效率**：派发次数、每次和合计的执行时间、token 用量（Codex 的输入、其中缓存、输出；设计负责人主会话和子代理的用量）、并行度、返工次数。数据缺失时写明原因。
- **质量**：测试数、CI、关键的实测数据、审查发现了多少、怎么处理的。
- **决定**：谁做了哪些决定。
- **问题与处理**：包括设计负责人自己的失误。
- **流程发现、遗留与下一步**。

## 不放

原始日志、git log、diff、评论全文。需要时给 issue 或 PR 的链接。细节只在影响判断时放，比如一次异常长的派发、一次返工的原因。

## 数据从哪里取

- **Codex**：工单验收评论里的派发数据。缺的从 `~/.codex/sessions/` 下的会话记录补：最后一个 `token_count` 事件里的 `total_token_usage`，`session_meta` 里的 `cwd` 对应是哪个 worktree。worktree 删掉后这些记录还在。
- **设计负责人主会话**：`~/.claude/projects/<项目目录>/<会话>.jsonl` 里每条回复的 `message.usage`。按 `message.id` 去重，跳过 `isSidechain` 的记录。
- **子代理**：任务通知里的 `subagent_tokens`。

范例：汇报目录里已有的汇报，目录见本仓库配置说明。
